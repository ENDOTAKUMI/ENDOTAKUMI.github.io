## コードレビューの目的

コードレビューは以下の目的で実施されます：

1. **コード品質の維持・向上**: バグの早期発見、可読性の向上、設計の改善
2. **知識の共有**: コードベースの理解を深め、チーム全体のスキルアップを図る
3. **一貫性の確保**: コーディング規約やアーキテクチャの方針を統一する
4. **ベストプラクティスの普及**: 効率的な実装方法や新しい技術の共有

## レビューのSLA（Service Level Agreement）

プルリクエストのレビューは、以下の時間内に開始することを目標とします：

- **内部チームのPR**: **48時間以内**に初回レビューを開始
- **外部チームのPR**: **48時間以内**に初回レビューを開始

### レビュー時間のガイドライン

- レビューは集中できる時間に実施する
- 1日の中で自然な区切りのタイミングで行う（例：午前の作業後、午後の作業前など）
- フロー状態を妨げないよう、適切なタイミングを選ぶ

### SLAを超えた場合

- 48時間を経過したプルリクエストについては、作成者がレビュアーにリマインドできます
- チームメンバーは互いに責任を持ち、SLAを遵守するよう心がけます

## レビューコメントのラベル

レビューコメントには視覚的に分かりやすいバッジを使用します。各コメントの冒頭にラベルを付けることで、優先度や性質を明確にします。

### ラベルの使い分け

| ラベル | 用途 | 説明 | 対応の必要性 |
| ------ | ---- | ---- | ------------ |
| ![must-badge](https://img.shields.io/badge/review-must-red.svg) | 必須の修正 | マージ前に必ず修正が必要な問題。バグ、セキュリティ上の問題、重大な設計上の欠陥など。 | **必須** |
| ![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg) | 質問 | コードの意図や実装の理由を確認したい場合。理解を深めるための質問。 | 回答推奨 |
| ![imo-badge](https://img.shields.io/badge/review-imo-orange.svg) | 個人的な意見 | 個人的な好みや代替案の提案。必ずしも変更を求めるものではない。 | 任意 |
| ![good-badge](https://img.shields.io/badge/review-good-brightgreen.svg) | 良い点 | 優れた実装や工夫を称賛する。ポジティブフィードバック。 | 対応不要 |
| ![nits-badge](https://img.shields.io/badge/review-nits-green.svg) | 些細な指摘 | タイポ、小さなスタイルの問題など。マージをブロックしない軽微な指摘。 | 推奨 |
| ![memo-badge](https://img.shields.io/badge/review-memo-lightgrey) | メモ | 参考情報や将来の改善案。今回の対応は不要。 | 対応不要 |
| ![next-badge](https://img.shields.io/badge/review-next-blueviolet) | 次回以降 | 今回のPRのスコープ外だが、将来対応すべき事項。別のIssue/PRで対応。 | 別途対応 |

### 使用例

```markdown
![must-badge](https://img.shields.io/badge/review-must-red.svg) この関数は入力値の検証が不足しています。null/undefinedの場合にエラーが発生する可能性があります。

![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg) なぜここでasync/awaitではなくPromise.then()を使用していますか？

![imo-badge](https://img.shields.io/badge/review-imo-orange.svg) 個人的には、この処理はカスタムフックに切り出した方が再利用性が高まると思います。

![good-badge](https://img.shields.io/badge/review-good-brightgreen.svg) エラーハンドリングが丁寧で、ユーザーフレンドリーなエラーメッセージになっています！

<!-- cspell:disable-next-line -->
![nits-badge](https://img.shields.io/badge/review-nits-green.svg) Typo: "sucessful" → "successful"
```

## レビュアーのためのガイドライン

### レビューの心構え

1. **建設的であること**: 批判ではなく、改善のための提案を行う
2. **明確であること**: 何が問題で、なぜそれが問題なのかを説明する
3. **敬意を持つこと**: コードではなく、人に対してコメントしない
4. **学びの機会とすること**: 新しいアプローチや技術を共有する

### 何を確認するか

レビューでは以下の観点から確認します:

#### 1. 設計

- [ ] コードは適切に設計されているか
- [ ] 変更は適切な場所に配置されているか
- [ ] この変更は今必要か、過度な設計になっていないか
- [ ] 既存のシステムと統合されているか

#### 2. 機能性

- [ ] コードは意図した通りに動作するか
- [ ] エッジケースが適切に処理されているか
- [ ] 並行処理やエラー処理は適切か
- [ ] ユーザーエクスペリエンスは良好か

#### 3. 複雑性

- [ ] コードは理解しやすいか
- [ ] 他の開発者がすぐに理解し、修正できるか
- [ ] 過度に複雑な部分はないか
- [ ] 必要以上にエンジニアリングされていないか

#### 4. テスト

- [ ] 適切なテストが含まれているか（ユニットテスト、統合テスト）
- [ ] テストは意味があり、適切に設計されているか
- [ ] テストは正しく、有用なアサーションを持っているか

#### 5. 命名

- [ ] 変数名、関数名、クラス名は明確か
- [ ] 名前は長すぎず、短すぎないか
- [ ] 名前から意図が理解できるか

#### 6. コメント

- [ ] コメントは明確で有用か
- [ ] コードが何をするかではなく、なぜそうするかを説明しているか
- [ ] 必要な場所にコメントがあるか（複雑なロジック、非自明な決定など）

#### 7. スタイルとドキュメント

- [ ] コーディング規約にしたがっているか
- [ ] ドキュメントは更新されているか（README、API仕様など）

#### 8. セキュリティ

- [ ] セキュリティの脆弱性はないか（XSS、SQLインジェクション、CSRF等）
- [ ] 機密情報が適切に扱われているか
- [ ] 入力値の検証は適切か

#### 9. パフォーマンス

- [ ] パフォーマンス上の問題はないか
- [ ] 不要な処理や計算はないか
- [ ] リソースは適切に管理されているか

### コメントの書き方

#### 良いコメントの例

```markdown
![must-badge](https://img.shields.io/badge/review-must-red.svg) ユーザー入力をそのままHTMLに挿入するとXSS脆弱性の原因になります。`sanitizeHtml()`または`DOMPurify`を使用してサニタイズしてください。

![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg) この`useEffect`の依存配列に`fetchData`が含まれていませんが、意図的ですか？これによって無限ループが発生する可能性があります。

![nits-badge](https://img.shields.io/badge/review-nits-green.svg) この変数名は`userData`より`user`の方がシンプルで読みやすいと思います。
```

#### 避けるべきコメントの例

```markdown
❌ このコード、意味わからないです。
✅ ![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg) このロジックの意図を教えていただけますか？複数の条件が複雑に絡み合っていて理解が難しいです。

❌ なんでこんな書き方するの？
✅ ![imo-badge](https://img.shields.io/badge/review-imo-orange.svg) この処理は配列メソッド（map/filter）を使うと、より宣言的で読みやすくなると思います。

❌ 間違ってます。
✅ ![must-badge](https://img.shields.io/badge/review-must-red.svg) この条件式は`&&`ではなく`||`を使うべきです。現在の実装では、両方の条件が真の場合のみ実行されてしまいます。
```

## 作成者のためのガイドライン

### 良いプルリクエストの作り方

1. **小さく保つ**
   - 1つのPRには1つの論理的な変更のみを含める
   - 可能な限り300行以下に抑える（大きすぎる場合は分割を検討）
   - 機能フラグを使用して、未完成の機能をマージできるようにする

2. **明確な説明を書く**
   - PRテンプレートを完全に埋める
   - 何を変更したか、なぜ変更したかを明確に記述
   - スクリーンショットやGIF動画を添付（UI変更の場合）

3. **セルフレビューを行う**
   - PRを作成する前に自分で一度レビューする
   - 不要なコメントや`console.log`を削除
   - フォーマットやlintエラーを修正

4. **テストを含める**
   - 新機能にはテストを追加
   - バグ修正の場合は、そのバグを検出するテストを追加
   - すべてのテストがパスすることを確認

5. **コンテキストを提供する**
   - 関連するIssueやドキュメントへのリンク
   - 設計上の決定の理由
   - トレードオフや代替案の考察（必要に応じて）

### レビューコメントへの対応

1. **![must-badge](https://img.shields.io/badge/review-must-red.svg) Must**: 必ず修正してください。修正後、レビュアーに再確認を依頼します。

2. **![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg) Ask**: 質問に丁寧に回答してください。必要に応じてコードにコメントを追加します。

3. **![imo-badge](https://img.shields.io/badge/review-imo-orange.svg) IMO**: 提案を検討し、採用する場合は修正、採用しない場合は理由を説明します。

4. **![nits-badge](https://img.shields.io/badge/review-nits-green.svg) Nits**: 可能な限り修正することを推奨しますが、マージはブロックされません。

5. **![next-badge](https://img.shields.io/badge/review-next-blueviolet) Next**: 別のIssue/PRを作成し、そこで対応します。リンクをコメントに残します。

6. **![memo-badge](https://img.shields.io/badge/review-memo-lightgrey) Memo / ![good-badge](https://img.shields.io/badge/review-good-brightgreen.svg) Good**: 対応不要です。感謝や「了解」を伝える簡単な返信は歓迎されます。

## ベストプラクティス

### 1. プルリクエストを小さく保つ

**なぜ重要か**:

- レビューが速く、正確になる
- バグの混入リスクが減る
- レビュアーの負担が減る
- マージの競合が減る

**実践方法**:

- 機能を小さな単位に分割する
- リファクタリングは別のPRにする
- 機能フラグを使用して段階的にリリースする

### 2. プルリクエストテンプレートを活用する

プロジェクトには`.github/pull_request_template.md`が用意されています。以下の情報を必ず記入してください:

- 変更の概要と目的
- 変更の種類（バグ修正、新機能、リファクタリング等）
- テスト手順
- 関連するIssue番号
- スクリーンショット（UI変更の場合）

### 3. 自動化を活用する

レビュアーが些細な問題に時間を費やさないよう、以下を自動化します:

- **Linter**: ESLint、Prettierなどでコードスタイルを統一
- **型チェック**: TypeScriptの型チェックを実行
- **テスト**: CI/CDパイプラインで自動テストを実行
- **セキュリティスキャン**: 依存関係の脆弱性チェック

これらのチェックは、プルリクエストのマージ前に自動的に実行され、失敗するとマージがブロックされます。

### 4. コンテキストの切り替えを最小限にする

- 作業中のタスクを中断してレビューする必要はありません
- 1日の中で自然な区切りのタイミングでレビューを行います
- 優先度の高いPRには「urgent」ラベルを付けることができます

## 避けるべきこと

### レビュアーが避けるべきこと

1. **自転車置き場の議論**: 本質的でない細かい好みの問題に時間を費やさない
   - ❌「この変数名は`data`より`information`の方が良いと思う」（明確な理由なく）
   - ✅「この変数名は`d`より`userData`の方が意図が明確になります」

2. **曖昧なコメント**: 何が問題で、どう改善すべきかを明確にする
   - ❌「このコードは良くない」
   - ✅「この処理は時間計算量がO(n²)です。Map/Setを使えばO(n)に改善できます」

3. **人格攻撃**: コードを批評し、人を批判しない
   - ❌「あなたはいつもこういうミスをしますね」
   - ✅「この部分は境界値のテストケースを追加すると良いでしょう」

4. **完璧主義**: すべてを完璧にしようとせず、「今より良くする」ことを目指す
   - 完璧なコードは存在しない
   - 今のPRで改善できることに集中する
   - ![next-badge](https://img.shields.io/badge/review-next-blueviolet)を活用して将来の改善を提案する

### 作成者が避けるべきこと

1. **大きすぎるPR**: 複数の機能や大規模なリファクタリングを一度に行わない

2. **説明不足**: コンテキストや変更の理由を省略しない

3. **防衛的な態度**: レビューコメントを個人攻撃と受け取らない
   - レビューはコード品質の向上が目的
   - 分からないことは質問する
   - 異なる意見は建設的に議論する

4. **テストの省略**:「後でテストを追加します」は避ける
   - テストはコードと同時に書く
   - どうしても難しい場合は![next-badge](https://img.shields.io/badge/review-next-blueviolet)でIssueを作成
